User-owned document. Not generated by AIOS, not inside an AIOS marker
block. Load on demand — non-trivial task, delegation, or when unsure

## Provider policy

**Codex is primary here** (personal project) — planning, implementation,
review, Harness, Team. **Claude is fallback**, used only once Codex
limits are exhausted or on explicit request. Gemini/OpenCode/Grok are not
used.

This is the exact opposite of the operator's work projects (Promo, AM,
etc.), where Claude is primary and Codex is fallback. Same AIOS
installation, same mechanism, different `.aios/model-registry.json` per
project — see below.

## Model routing — how the split actually works

AIOS reads its model registry from ONE global path by default, shared by
every project on this machine. To let this project and the work projects
disagree, the operator had the loader
(`C:/Users/Yurii/.rexcil/aios/scripts/lib/model-router/registry.mjs`)
patched to check `<cwd>/.aios/model-registry.json` first, falling back to
the global/built-in registry if absent. `.aios/model-registry.json`
committed here is that project-local override — do not delete it, and if
AIOS `update`/`setup` ever regenerates the global registry, this file is
unaffected.

Ladder used in this project (task type → primary → fallback):

| Task type | Primary | Fallback |
|---|---|---|
| architecture / global decisions | `gpt-5.6-sol` | `gpt-5.5` → `claude-opus` |
| planning, code-review, security-review | `gpt-5.6-terra` | `gpt-5.6-sol` → `claude-sonnet` |
| implementation, testing, frontend, self-healing, browser-automation | `gpt-5.6-terra` | `gpt-5.6-luna` → `claude-sonnet` |
| research | `gpt-5.5` | `gpt-5.6-sol` → `claude-sonnet` |
| docs / routine | `gpt-5.6-luna` | `gpt-5.6-terra` → `claude-sonnet` |

`gpt-5.6-sol` is reserved for genuine architecture/global-decision
signals only — it is not the default for planning or implementation.

Inspect a live decision:

```bash
node "C:/Users/Yurii/.rexcil/aios/scripts/aios.mjs" model-router route --task "<text>" --explain --json
```

**Known quirk (pre-existing AIOS behavior, not introduced by this setup):**
task text containing both an architecture signal and planning-intent
language (e.g. "design the architecture...") can get overridden by
AIOS's own IntentGate back down to the `planning` taskType instead of
`architecture`. Phrase architecture-only requests without "design/plan"
wording if you specifically need the top tier to trigger.

**"Fallback" is advisory, not automatic failover.** AIOS does not detect
quota-exhaustion and auto-retry with the next model in `fallback` — that
array is informational (shown by `--explain`) only. Switching to Claude
when Codex limits are hit is a manual call: pass `--provider claude` to
`harness run` / `team`, or just tell the assistant Codex is out of quota.

## Task classification

Same direct/guarded/planned split as the AIOS native block in `CLAUDE.md`
defines. `direct` = one-file mechanical change, no memory search needed.
`guarded` = normal implementation/debug, memory + Codemap impact check
first. `planned` = architecture, multi-module changes, high regression
risk — full context → plan → implement → independent review → verify →
persist.

## Codemap

`code-review-graph` MCP is installed and the graph is built (321 files,
~3300 nodes at setup time). Same tool, same usage pattern as Promo:
memory → Codemap → targeted reads → broad scan only as a last resort.
Budget ≤3 graph calls per work item.

## Session continuity

Same as Promo: for work that outlives one chat, either rely on the
Harness run journal (`harness status --session <id>`) or write one
`ACTIVE:` memo (objective · done · decisions · verification · blockers ·
next steps · files) via `aios memo add`.

## Context budget

Do not load all memory, re-scan the whole repo, or re-read large files
without a concrete reason. relevant memory → relevant graph → relevant
source → execute.

## Known limitations

- Custom per-role names (e.g. a hypothetical `game-architecture` role) are
  **not supported** by the installed AIOS orchestrator — it hardcodes
  exactly 4 roles (`planner`, `implementer`, `reviewer`,
  `security-reviewer`). Tier separation for "real architecture work" is
  achieved through task-type signal detection (see IntentGate quirk
  above), not through custom role names.
- The AIOS install itself (`C:/Users/Yurii/.rexcil/aios`) is not a git
  repo; the loader patch there is backed up manually (not via git), same
  copies referenced from Promo's own workflow doc.
