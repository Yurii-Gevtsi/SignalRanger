# Minimal construction: runtime-каталог 41 одиниці

## Reuse ladder

1. **Не робити нову структуру:** відхилено. Чинний каталог містить 17 legacy
   записів і не може правдиво представляти 41 канонічний `weaponId`.
2. **Повторно використати наявні data-layer типи:** прийнято.
   `WeaponProgressionDefinition`, `WeaponCatalogAvailability` і
   `PrototypeWeaponLibrary` уже є спільними входами для Shop, Arsenal,
   Workshop, save та EditMode тестів.
3. **Мова/стандартна бібліотека:** достатні. Наявні масиви та словники C# не
   потребують сторонніх залежностей.
4. **Встановлені залежності:** не потрібні. Новий пакет чи runtime-сервіс лише
   розширив би зв'язність без додаткової поведінки.
5. **Один локальний вираз:** відхилено. Тримати 41 джерело отримання окремими
   switch-виразами в UI призведе до розходження магазину, арсеналу й майстерні.
6. **Мінімальна нова конструкція:** доповнити наявний runtime-каталог повними
   даними 41 одиниці та зробити `WeaponCatalogAvailability` єдиним читачем
   їхнього джерела. Додати відсутні prototype-записи як data-only визначення;
   бойові ефекти для тих, що ще не реалізовані, лишаються поза межами зміни.

## Обраний варіант

Єдина data-driven проєкція канонічної таблиці:

```text
WeaponProgressionCatalog (рівень, ТТХ, особливості)
        ├── WeaponCatalogAvailability (starter/core/arena/dungeon/boss)
        ├── PrototypeWeaponLibrary (визначення для UI та інвентарю)
        ├── ShopScreenController (лише coreShop)
        ├── WeaponsScreenController (усі активні власні)
        └── ArchitectScreenController (усі активні власні з розвитком)
```

Обрано замість нової бази конфігів, бо перелічені точки вже є публічними
runtime-входами й не дублюють дані у UI. Подальший перехід на ScriptableObject
можливий окремою міграцією без зміни цих контрактів.
