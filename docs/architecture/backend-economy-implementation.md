# Бекенд для економіки та прогресії: план імплементації

Статус: прийнято (2026-07)
Джерело вимог: «Прогресія, економіка та арсенал» v1.1 (дизайн-документ, липень 2026)
Пов'язані документи: `backend-online-services.md`, `docs/setup/ugs-setup.md`

Цей документ мапить фінальний план економіки на заплановану бекенд-архітектуру
(UGS, offline-first, усе за власними інтерфейсами) і визначає, що саме треба
реалізувати на бекенді для кожного етапу дизайн-плану.

## 1. Аналіз відповідності

### Лягає на заплановану архітектуру без змін

- **Абонемент $4.99** — це наша вже спроєктована схема разового 30-денного
  пропуску: consumable IAP → Cloud Code валідує чек → protected-ключ
  `premiumExpiresAt`. Auto-renewable підписки не потрібні (аналітична подія
  `subscription_renewed` = повторна покупка).
- **Receipt validation** (етап 4 дизайн-плану) — уже заплановано:
  Cloud Code + Google service account (Android Publisher API).
- **«Числа — гіпотези, перебудувати за телеметрією»** — прямий мандат на
  Remote Config для всіх економічних параметрів + UGS Analytics.
- **PvP (етап 6)** — збігається з нашим етапом 2: server-валідація результату
  через Cloud Code, нормалізація — конфігом.
- **Offline-first** — «без енергії, без таймерів, поразка теж дає нагороду»
  сумісне з локальною грою; ціннісні нарахування синхронізуються (див. §4).

### Уточнює вже прийняті рішення

- **Джерела істини розширюються**: тепер серверними цінностями є не лише
  валюта й пропуск, а й кристали, креслення, чипи перекалібрування,
  токени події, entitlements (starter pack, косметика).
- **Бонуси пропуску (+10% кредитів/креслень, 120 кристалів, чип, reroll)**
  означають, що *нарахування нагород має відбуватись у Cloud Code* — саме там
  застосовуються множники пропуску і рекламні бонуси. Клієнт лише показує.

### Нове для бекенду (не було в архітектурному документі)

1. **Ідемпотентний ledger** — вимога дизайн-документа §5/§14.1: усі видачі
   як транзакції з `transactionId`/`idempotencyKey`.
2. **Черга офлайн-нагород** — гра грабельна офлайн, а валюта серверна;
   потрібен механізм відкладеної фіксації (див. §4).
3. **Daily login / daily / weekly** — серверна межа доби, стріки, reroll.
4. **Денні капи rewarded-реклами** — серверний лічильник, скидання за добою.
5. **Respec** (кристали/чип, повернення 100% креслень і 80% кредитів) —
   серверна транзакція.
6. **Життєвий цикл івенту** — токени, доріжка, конвертація залишку після
   завершення, Архів із націнкою 125%.
7. **Набір аналітичних подій** (§14.2) і балансові сигнали (§14.3).

### Обмеження, яке треба знати

UGS не має запитуваної реляційної БД. Тому:

- ledger-дедуплікація — ковзне вікно оброблених `idempotencyKey`
  у protected-даних гравця (див. §4), а не вічна історія;
- повний аудит-трейл — це події Analytics (`reward_granted` з transactionId),
  за потреби — експорт Analytics для розслідувань;
- якщо колись знадобиться справжній запитуваний ledger по всіх гравцях —
  це додатковий тригер етапу 3 (власний сервіс + PostgreSQL),
  куди ledger переїде першим.

## 2. Валюти й ресурси → UGS

| Ресурс (дизайн-док) | Реалізація | Хто пише |
|---|---|---|
| Кредити | Economy currency `CREDITS` | тільки Cloud Code |
| Квантові кристали | Economy currency `CRYSTALS` | тільки Cloud Code |
| Креслення | лічильники **на одиницю зброї/систему дроїда** в protected Cloud Save (`blueprints.<weaponId>`) | тільки Cloud Code |
| Чип перекалібрування | Economy inventory item `RESPEC_CHIP` | тільки Cloud Code |
| Навігаційні ядра | частина `MissionProgress` у сейві (сюжетний прапорець, не валюта) | клієнт (PvE-прогрес) |
| Токени події | protected-ключ `event.<eventId>.tokens` | тільки Cloud Code |
| Entitlements (пропуск, starter pack, косметика) | protected-ключі + Economy inventory для косметики | тільки Cloud Code |

Чому креслення не Economy-валюта: дроп іде з пулу «відкрита й не максимальна»
конкретна одиниця, тобто креслення прив'язані до одиниці (24 типи на релізний
каталог + лінії дроїда). Мапа лічильників в одному protected-ключі простіша
за 30 валют у каталозі Economy і однаково проходить через ledger Cloud Code.

Примітка: у §14.1 дизайн-доку `Wallet.blueprints` — одне поле; трактуємо його
як мапу `weaponId → count` відповідно до правил дропу §4.3/§9.1. Якщо
дизайн-рішення зміниться на «загальні креслення», міняється лише схема ключа.

## 3. Модель даних §14.1 → де живе

| Сутність | Тип | Де |
|---|---|---|
| WeaponDefinition, WeaponUpgradeNode | статичний конфіг | ScriptableObject (defaults) + Remote Config (тюнінг: ціни, statDelta, usesPerBattle, powerBudget) |
| PlayerWeapon (rank, branch) | стан гравця, цінність | protected Cloud Save `weapons.<id>`, зміни через Cloud Code |
| DroneBuild | стан гравця, цінність | protected Cloud Save `drone`, зміни через Cloud Code |
| Wallet | цінність | Economy + protected keys (§2) |
| RewardTransaction | ledger | §4 |
| MissionProgress | PvE-прогрес | локальний `SaveData` + дзеркало у звичайному Cloud Save |
| EventProgress | цінність (нагороди) | protected Cloud Save `event.<eventId>` |
| Entitlement | цінність | protected keys (§2) |

Принцип поділу той самий, що в `backend-online-services.md`: PvE-прогрес і
налаштування — локально з дзеркалом; усе, що конвертується в цінність, —
тільки через Cloud Code у protected-дані.

## 4. Ledger, ідемпотентність і офлайн-черга

Єдина точка нарахувань — Cloud Code функція `GrantRewards`
(викликається іншими функціями, не клієнтом напряму).

**Транзакція** (формат із §14.1): `transactionId` (guid, генерує клієнт),
`sourceType` (battle/mission/daily/weekly/login/ad/event/purchase/respec),
`sourceId`, `rewards`, `createdAt`.

**Ідемпотентність**: Cloud Code тримає в protected-даних гравця ковзне вікно
оброблених `transactionId` (останні ~200 або 30 днів). Повторний виклик із
тим самим id повертає перший результат і нічого не нараховує.

**Офлайн-черга**: клієнт грає PvE без мережі; кожен завершений бій/місія
створює локально запис транзакції у чергу в `SaveData`. При появі мережі
черга зливається у `SubmitBattleResult`/`ClaimReward` по одній; успішно
зафіксовані видаляються. Локальний баланс, показаний офлайн, — оптимістичний
кеш; після зливу черги клієнт читає авторитетний баланс.

**Sanity-перевірки при фіксації** (параметри — з Remote Config):

- нагорода за бій ≤ максимуму режиму + performance cap (+30% кредитів / +10% креслень);
- поразка = 40–60% бази, без performance bonus;
- мінімальна тривалість бою; максимум боїв за добу для нарахувань
  (м'який cap проти явного абьюзу, не проти гравця);
- повтор кампанії = 40% первинної нагороди; перше проходження місії —
  одноразове (`MissionProgress.rewardClaimed`);
- дроп креслень — тільки для відкритих і не максимальних одиниць.

## 5. Функції Cloud Code (повний список)

Етап A (ledger + мета):

- `SubmitBattleResult` — фіксація бою, розрахунок нагороди з множниками
  (пропуск +10%, rewarded +50%), дроп креслень із пулу, ідемпотентно.
- `ClaimMissionReward` — сюжетні/експертні/зіркові нагороди, одноразовість.
- `ClaimDailyLogin` — стрік 1–7, серверна межа доби (UTC), нагорода дня.
- `ClaimQuestReward` — daily/weekly, перевірка виконання за лічильниками
  з батл-результатів; `RerollDailyQuest` (1 базовий + 1 від пропуску).
- `GetServerTime`, `GetPlayerEconomyState` — час і знімок балансів/лічильників.

Етап B (покупки й прокачка):

- `ValidatePurchase` — чек IAP → кристали / starter pack / пропуск.
- `GrantPremiumPass` — `premiumExpiresAt` +30 днів (продовження), разом із
  разовою видачею 120 кристалів і 1 чипа на цикл пропуску.
- `PurchaseWeapon` — списання кредитів за каталожною ціною з Remote Config.
- `UpgradeWeaponRank` — ранги 2–10: списання кредитів+креслень, вибір гілки
  на 5/10.
- `RespecWeaponBranch` — чип або 50 кристалів; повернення 100% креслень,
  80% кредитів; один безкоштовний під час навчання (прапорець).
- `UpgradeDroneSystem` — корпус/гусениці/прискорювач/приціл.
- `RegisterAdReward` — інкремент денного лічильника, перевірка капів
  (3/бій у PvE, денний cap на +50%), видача бонусу.

Етап C (івенти):

- `ClaimEventNode` — доріжка події, токени.
- `ConvertExpiredEventTokens` — при першому логіні після завершення події,
  за курсом із Remote Config.
- `PurchaseArchiveWeapon` — 125% ціни аналога + архівні креслення.

Етап D (PvP, за планом етапу 2 архітектури): `SubmitPvpResult`
із подвійним підтвердженням (обидва клієнти) і sanity-перевірками.

## 6. Remote Config: групи ключів

Усе з §10 дизайн-доку — тюнінг без релізу:

- `economy.rewards.*` — таблиці нагород за режимами, performance cap,
  відсоток за поразку/повтор;
- `economy.prices.weapons.*`, `economy.prices.ranks.*` — вартості;
- `economy.pass.*` — множники (+10%), місячні кристали (120), ціна respec;
- `ads.caps.*` — денні капи, кап за бій;
- `quests.*` — набори daily/weekly, пороги, нагороди;
- `events.<eventId>.*` — розклад (start/end), доріжка, курс конвертації,
  націнка Архіву;
- `balance.softcap.*` — soft cap сили за системами (§6.3 дизайн-доку).

Конфіги — у репозиторії, деплой через Deployment package (правило
config-as-code із `backend-online-services.md`).

## 7. Аналітика

UGS Analytics, кастомні події точно за §14.2 дизайн-доку:
`battle_started/finished`, `reward_granted` (з transactionId і adMultiplier —
це і є аудит-трейл ledger), `weapon_unlocked/upgraded`, `mission_blocked`,
`ad_offer_shown/accepted/completed`, `subscription_started/renewed/cancelled`
(renewed = повторна покупка пропуску), `event_node_claimed`,
`daily_login_claimed/daily_quest_completed`.

Балансові сигнали §14.3 (частка використань зброї >25–30%, win rate власників
івентної зброї, >20% гравців у level gate, ріст балансів без витрат) —
дашборди на цих подіях; перевіряти щотижня після soft launch.

## 8. План робіт (мапа на етапи дизайн-документа)

Етапи 0–2 дизайн-доку (правила, vertical slice, MVP кампанії) — **бекенд не
потрібен**: локальний `SaveData`, no-op інтерфейси, локальні нагороди.
Підготовка в коді клієнта: усі нарахування вже зараз проводити через
`IEconomyService` з транзакційним форматом (transactionId у локальному
ledger) — тоді підключення Cloud Code буде заміною адаптера.

### Дизайн-етап 3 «мета й soft launch» → бекенд-етапи 1 + A

- [ ] UGS фундамент за `ugs-setup.md` (проєкт, environments, Auth+GPGS, Cloud Save дзеркало, Remote Config)
- [ ] Economy: `CREDITS`, `CRYSTALS`; схема protected-ключів (§2)
- [ ] Ledger: `GrantRewards` + ідемпотентне вікно + офлайн-черга в клієнті
- [ ] `SubmitBattleResult` із sanity-перевірками і дропом креслень
- [ ] `UpgradeWeaponRank`, `UpgradeDroneSystem`, `PurchaseWeapon`
- [ ] Daily login / daily / weekly / reroll (`ClaimDailyLogin`, `ClaimQuestReward`)
- [ ] Remote Config групи `economy.*`, `quests.*`
- [ ] Analytics: базовий набір подій
- [ ] Міграція `SaveData`: винесення цінностей у серверний стан (чергова `ISaveMigration`)

### Дизайн-етап 4 «монетизація» → бекенд-етап 1.5 + B

- [ ] Множники пропуску в `GrantRewards` (+10%, не діє на токени події та одноразові сюжетні)
- [ ] `RegisterAdReward` + денні капи; чесний таймер капу в UI
- [ ] `RespecWeaponBranch`

### Дизайн-етап 5 «live events» → бекенд-етап C

- [ ] `events.*` у Remote Config (розклад без релізу)
- [ ] `ClaimEventNode`, токени, `ConvertExpiredEventTokens`

- [ ] Prestige-повтор події (косметичний рівень власникам)

### Дизайн-етап 6 «PvP prototype» → бекенд-етап 2 (без змін)

За `backend-online-services.md`; додатково з дизайн-доку: нормалізація рангів
і статів дроїда конфігом, 8-слотовий loadout — валідація складу в Cloud Code,
rewarded/PvE-бонуси в PvP вимкнені на рівні `RegisterAdReward` (режим у контексті).

## 9. Рішення, які треба зафіксувати до бекенд-етапу A

1. **Креслення: за одиницею чи загальні** — прийнято «за одиницею» (§2);
   якщо дизайн вирішить інакше, змінюється схема ключа й пул дропу.
2. **Межа доби** — рекомендація: UTC-доба за серверним часом для капів і
   daily (просто і несхильне до маніпуляцій годинником; недолік — «новий
   день» настає для гравця не опівночі; альтернатива з фіксованим зсувом
   часового поясу гравця складніша й відкладена).
3. **Розмір вікна ідемпотентності** — 200 транзакцій / 30 днів (старіші
   дублікати неможливі, бо черга клієнта зливається при першому ж конекті).
4. **М'який добовий cap боїв для нарахувань** — значення в Remote Config;
   потрібна цифра від дизайну (анти-абьюз, не обмеження гри).
