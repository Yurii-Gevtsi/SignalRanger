# Бекенд і онлайн-сервіси: архітектура та план розвитку

Статус: прийнято (2026-07)
Пов'язані документи: `target-architecture.md`, `iteration-1-soft-launch-foundation.md`,
`backend-economy-implementation.md` (мапа фінального плану економіки на цю архітектуру)

## Рішення

Бекендом гри на етапах софт-лончу та раннього росту є **Unity Gaming Services (UGS)** —
managed BaaS без власних серверів. Власний сервіс (ASP.NET Core + PostgreSQL)
не піднімається «про запас»; для нього зарезервоване місце в архітектурі,
і він з'являється лише при настанні конкретних тригерів (див. «Етап 3»).

Чому UGS, а не власний сервер одразу:

- покрокова гра генерує одиниці запитів за бій — free tier UGS покриває
  розробку, софт-лонч і перші тисячі-десятки тисяч MAU;
- готові ігрові підсистеми (Auth, Cloud Save, Economy, Remote Config,
  Cloud Code, Lobby/Relay) замість місяців бекенд-розробки;
- нуль операційного навантаження (аптайм, бекапи, безпека);
- нативна інтеграція з Unity та єдиний player ID для всіх сервісів.

Чому не Firebase/Supabase: немає ігрових підсистем (економіка, валідація
покупок, лідерборди) — їх довелося б збирати самостійно.

## Базові принципи

1. **Offline-first.** Локальний сейв (`ISaveService` + `JsonFileSaveService`)
   лишається джерелом істини для геймплею. Гра повністю грабельна без мережі.
   Хмара — синхронізація і авторитет для «цінного».
2. **Усі SDK за власними інтерфейсами** (правило `target-architecture.md`).
   UI і gameplay не знають про існування UGS. Кожен онлайн-сервіс має
   no-op/локальну реалізацію для editor/offline.
3. **Джерело істини за типом даних** (див. таблицю нижче).
4. **Тільки серверний час** для будь-яких таймерів цінностей
   (преміум-пропуск, daily rewards). Годинник пристрою — лише fallback-кеш.
5. **Клієнт не може писати цінності напряму.** Валюта, покупки, пропуск —
   тільки через Cloud Code / Economy (protected-дані).
6. **Config-as-code.** Конфіги Economy/Remote Config/Cloud Code зберігаються
   в репозиторії та деплояться через Deployment package / UGS CLI,
   а не редагуються руками в дашборді.
7. **Усі нарахування — ідемпотентні транзакції.** Кожна видача нагороди має
   `transactionId`; повторний запит не дублює валюту. Формат єдиний для
   локального (офлайн) і серверного ledger — див.
   `backend-economy-implementation.md`.

### Джерела істини

| Дані | Джерело істини | Механізм |
|---|---|---|
| Налаштування, туторіал | Локальний сейв | дзеркало в Cloud Save |
| Прогрес кампанії/місій, статистика | Локальний сейв | дзеркало в Cloud Save |
| Кредити, кристали, креслення | Етапи 0-2 дизайн-плану: локально → soft launch: сервер | Economy + ledger у Cloud Code |
| Ранги/гілки зброї, апгрейди дроїда | Сервер (після soft launch) | protected keys, пише Cloud Code |
| Покупки (IAP), entitlements | Сервер | Cloud Code валідує чек |
| Преміум-пропуск | Сервер | protected key `premiumExpiresAt` |
| Токени події, прогрес івентів | Сервер | protected keys, пише Cloud Code |
| Результат PvP-бою | Хост-клієнт + sanity-перевірки Cloud Code | Етап 2 |
| Баланс/тюнінг | Remote Config | ScriptableObject як defaults |

Деталі економічної частини (ledger з ідемпотентними транзакціями,
офлайн-черга нагород, daily/weekly, рекламні капи, івенти, Архів) —
у `backend-economy-implementation.md`.

## Інтерфейси (Core) та адаптери (Infrastructure)

Нові інтерфейси додаються поетапно, у стилі наявного `ISaveService`:

```text
Core (інтерфейси)                Infrastructure (адаптери)
IAuthService                     UgsAuthService, NoOpAuthService
ICloudSyncService                UgsCloudSaveSyncService, NoOpCloudSyncService
IServerEconomyService            UgsEconomyService, LocalEconomyService
IPremiumStatusService            UgsPremiumStatusService, NoOpPremiumStatusService
IRemoteConfigService (є)         UgsRemoteConfigService
IPurchaseService (є)             UnityIapPurchaseService
IServerTimeService               UgsServerTimeService (кеш + offline fallback)
IPvpSessionService (етап 2)      UgsRelayPvpSessionService
IMatchmakingService (етап 2)     UgsMatchmakerService
```

Composition root (`AppServices`/`GameBootstrapper`) обирає реалізації:
offline/editor збирається з no-op, продакшн — з UGS-адаптерами.
Заміна UGS на власний сервіс у майбутньому = заміна адаптерів.

## Автентифікація

Мета — «гра просто працює»: без екранів логіну, з автоматичною прив'язкою
Google Play акаунту при першому запуску (як у більшості мобільних ігор).

Потік при старті:

1. Спроба **автоматичного входу Google Play Games** (GPGS v2 робить це сам
   при запуску, без діалогів, якщо у гравця ввімкнений auto sign-in).
2. Успіх → `SignInWithGooglePlayGamesAsync(authCode)` в Unity Authentication:
   UGS-акаунт створюється/знаходиться за Google Play ідентичністю.
   Прогрес автоматично переноситься між пристроями.
3. Відмова/недоступність GPGS → **анонімний вхід** (стабільний player ID
   без жодних дій гравця; session token кешується на пристрої).
4. У налаштуваннях — кнопка «Прив'язати акаунт»
   (`LinkWithGooglePlayGamesAsync`) для тих, хто почав анонімно.
5. iOS пізніше: той самий патерн із Sign in with Apple / Game Center.

Правило мержу акаунтів: якщо при вході через Google Play на новому пристрої
знайдено наявний хмарний прогрес — конфлікт вирішується на користь
акаунту з більшим прогресом, із підтвердженням гравця в UI.

## Синхронізація сейву

- Локальний `SaveData` (версійований, з наявними міграціями) пушиться
  в Cloud Save у ключових точках: кінець бою, покупка, згортання застосунку.
- Пул — при логіні та при вході на новому пристрої.
- Конфлікт визначається за версією + таймстемпом; авто-вибір «новішого»,
  при суттєвій розбіжності — вибір гравця.
- Наявний механізм `ISaveMigration` використовується і для хмарних даних
  (мігрує той самий `SaveData`).
- Cloud Save метрований: жодних читань «на кожен екран», тільки
  згадані точки синхронізації.

## Преміум-пропуск / абонемент $4.99 (разова покупка на 30 днів)

Не auto-renewable підписка сторів, а consumable IAP + серверна дата:

1. Покупка «Абонемент 30 днів» через Unity IAP (consumable).
2. Cloud Code валідує чек і пише `premiumExpiresAt = serverNow + 30d`
   у **protected**-ключ Cloud Save (клієнт читає, писати не може);
   тією ж транзакцією видаються разові бонуси циклу
   (120 кристалів, 1 чип перекалібрування).
3. Клієнт: `IPremiumStatusService.IsActive` = `premiumExpiresAt > serverNow`;
   значення кешується локально і коректно «згасає» офлайн, бо це фіксована дата.
4. Повторна покупка при активному пропуску — продовження (+30 днів
   до поточної дати закінчення).
5. Refund-відкликання (Google Voided Purchases API) — свідомо відкладено;
   додається пізніше в Cloud Code без змін клієнта.

Постійні ефекти абонемента (+10% кредитів/креслень, auto-rewarded бонуси,
+1 reroll daily) застосовуються **на сервері** в момент нарахування нагород
(Cloud Code), а не в клієнті; параметри — з Remote Config, щоб тюнити без
релізу. Повний перелік бонусів і обмежень — у дизайн-документі економіки
та `backend-economy-implementation.md`.

## PvP (покроковий, 30 с на хід, бій до 5 хв)

- **Matchmaker/Lobby** — пошук суперника, кімната на двох.
- **Relay + Netcode for GameObjects** — канал між клієнтами; хостом
  виступає один із гравців (стандартна практика для casual покрокових ігор).
- **По мережі передаються команди ходу** (кут, сила, зброя, переміщення —
  десятки байтів), а не потік стану. Обидва клієнти відтворюють хід локально
  спільною симуляцією (див. `battle-simulation-extraction.md`).
- **Хост авторитетний, і на межі кожного ходу публікує свій стан**, під який
  клієнт себе коригує. Це не чистий lockstep: `battle-simulation-extraction.md`
  (етап C) фіксує, що детермінізм гарантований лише в межах однієї платформи,
  тож на реальному парку пристроїв float-математика розходиться. Межа ходу
  квіесцентна (снаряди відпрацювали, юніти сіли), тому корекція там дешева й
  майже непомітна. Ландшафт передається кратерами (центр+радіус), не маскою.
  Обґрунтування вибору — `../design/raid-and-pvp-battle-modes.md`, фаза 5.
- Результат бою фіксує Cloud Code із sanity-перевірками
  (мінімальна тривалість бою, максимум нагороди за бій тощо).
- Орієнтовний трафік: ~10 метрованих запитів UGS і кілька КБ через Relay
  на бій. Free tier Relay (~50 середніх CCU) ≈ 4-5 тис. щоденних
  PvP-гравців при ~15 хв PvP на день.
- Server-authoritative арбітраж — лише якщо/коли з'явиться ranked
  (це тригер етапу 3, не раніше).

## План розвитку

### Етап 0 — зараз (виконується)

Локальний сейв, no-op онлайн-інтерфейси. Ніякого бекенду.
Підготовка: тримати `SaveData` чистим версійованим DTO (вже так).

### Етап 1 — фундамент онлайну (перед софт-лончем)

- [ ] Unity Cloud проєкт, environments `development`/`production`
- [ ] Authentication: анонімний вхід + session persistence
- [ ] Автовхід Google Play Games (GPGS v2) + link для анонімних
- [ ] Cloud Save: дзеркало `SaveData`, конфлікт-резолюція
- [ ] Remote Config за наявним `IRemoteConfigService`
- [ ] Config-as-code: Deployment package, конфіги в репозиторії

### Етап 1.5 — монетизація (одразу за етапом 1)

- [ ] Economy: валюта(и), цінники з конфігів у репозиторії
- [ ] Unity IAP + валідація чеків у Cloud Code
- [ ] Преміум-пропуск за схемою вище
- [ ] Міграція нарахування валюти: клієнт → Cloud Code
- [ ] Алерти free tier (75%/100%), платіжна картка в org

Детальна розбивка етапів 1/1.5 під фінальний план економіки (ledger,
daily/weekly, рекламні капи, respec, івенти) —
у `backend-economy-implementation.md`, §8.

### Етап 2 — PvP (після стабілізації core game)

- [ ] Lobby + Relay + Netcode, client-host 1v1
- [ ] Детермінований протокол команд ходу поверх спільної симуляції
- [ ] Matchmaker (спершу можна простий випадковий підбір через Lobby)
- [ ] Фіксація результату через Cloud Code + sanity-перевірки
- [ ] Reconnect у межах бою (повторне під'єднання до Relay-сесії)

### Етап 3 — власний сервіс (за тригерами, не за календарем)

Тригери (будь-який):

1. Cloud Code стає тісним для кастомної серверної логіки.
2. Ranked PvP вимагає server-authoritative симуляції боїв
   (Unity Multiplay закрито 03.2026 — виділені сервери це Edgegap/Gameye/власні).
3. Місячний рахунок UGS стабільно перевищує вартість власної
   інфраструктури + часу на її підтримку.

Форма: тонкий ASP.NET Core сервіс + managed PostgreSQL, який
**співіснує** з UGS (валідує JWT Unity Authentication через публічні
ключі, працює з UGS через service account), а не замінює його одномоментно.
Перенос підсистем — по одній, заміною адаптерів за наявними інтерфейсами.

## Ризики та обмеження

- Перевищення free tier без доданої платіжної картки може загейтити
  доступ до API → картку додати на етапі 1, алерти ввімкнути.
- Квоти free tier Unity періодично змінює → перед етапом 1 звірити
  з pricing estimator; цифри в цьому документі орієнтовні.
- Хост-клієнт у PvP може махлювати → прийнятно для casual;
  sanity-перевірки в Cloud Code обмежують шкоду; ranked без
  server authority не запускати.
- Vendor lock-in UGS → пом'якшується шаром інтерфейсів і config-as-code
  у репозиторії.
