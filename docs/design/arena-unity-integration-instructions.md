# Інструкції для інтеграції модульних руйнівних арен у Unity

## Межі відповідальності

Цей документ застосовується в основному Unity-проєкті після завершення роботи над візуальними файлами арени.

Візуальний проєкт передає:

- master і preview;
- окремі background-зображення;
- обрізані visual PNG руйнівних елементів;
- відповідні mask PNG;
- CSV із координатами та sorting order.

Unity-проєкт відповідає за імпорт, складання prefab, позиціонування, спільну collision grid, попіксельне руйнування, пам'ять, продуктивність і тести.

## Правила приймання ассетів

1. Не редагувати оригінальні source-файли візуального проєкту.
2. Копіювати тільки затверджену версію арени в окрему директорію контенту.
3. Перед імпортом перевірити наявність visual, mask і запису CSV для кожного руйнівного елемента.
4. Перевірити, що розміри visual та mask збігаються піксель-в-піксель.
5. Зафіксувати розмір віртуального production-полотна, `production_scale` і спільний Pixels Per Unit у конфігурації арени.
6. Перед широкою зміною поточного `BattleTerrain` спочатку погодити архітектуру й задокументувати рішення.

Запечена світла шахова підкладка, маджента або інший фон у `*_visual.png` є дефектом штатного результату: для нових ассетів потрібен справжній alpha-канал. Такий source допускається лише як аварійний fallback за умови якісної маски того самого розміру та обов'язкового створення чистого RGBA output.

## Аварійне автоматичне відновлення прозорості

Source-файли з візуального проєкту не редагувати. Перед Unity-імпортом editor preprocessing має створити окремий очищений RGBA PNG:

1. Відкрити пару `*_visual.png` і `*_mask.png` та перевірити однакові розміри.
2. Побудувати alpha-канал із яскравості маски: біле є непрозорим матеріалом, чорне — прозорою ділянкою, сірі краї дають згладжений alpha.
3. Для collision mask окремо застосувати контрольований поріг, не використовуючи згладжений visual alpha як фізичну твердість.
4. Видалити вплив шахової підкладки з напівпрозорих крайових пікселів або замінити їхній RGB кольором найближчого непрозорого пікселя об'єкта.
5. Виконати color dilation на кілька пікселів за межі силуету, щоб Bilinear-фільтрація не створювала світлого ореолу.
6. Записати результат у керовану generated-директорію основного проєкту, не перезаписуючи source visual.
7. Перевірити очищений спрайт на темному, світлому та кольоровому фоні при масштабі 100% і 200%.

Ця обробка має бути автоматичною та повторюваною для кожної арени. Ручне стирання шахової підкладки для кожного елемента не допускається.

## Рекомендована структура Unity

```text
ArenaComposition
├── BackgroundRoot
└── DestructibleWorld
    ├── DestructibleSurface_Ground_01
    ├── DestructibleSurface_Ship_01
    ├── DestructibleSurface_Crate_01
    └── DestructibleSurface_...
```

Основні відповідальності:

- `ArenaComposition` створює арену з manifest/config і володіє її root-об'єктом;
- `DestructibleSurface` володіє окремою visual texture, mask і перетворенням world-to-pixel;
- `DestructibleWorld` зберігає спільну world-space collision grid;
- реєстр поверхонь знаходить усі фрагменти, яких торкається вибух;
- система вибуху застосовує один crater до всіх поверхонь у зоні ураження;
- фон не реєструється в системі руйнування.

## Імпорт текстур

Рекомендовані налаштування visual PNG:

```text
Texture Type: Sprite (2D and UI)
Sprite Mode: Single
sRGB: On
Alpha Source: Input Texture Alpha
Alpha Is Transparency: On
Non Power of 2: None
Generate Mip Maps: Off
Filter Mode: Bilinear
Wrap Mode: Clamp
Sprite Mesh Type: Full Rect
Pixels Per Unit: 256
```

Android production:

```text
Override for Android: On
Max Size: відповідно до фактичного PNG, максимум 4096
Format: ASTC 4x4
Compressor Quality: Best
Crunch: Off
```

RGBA32 використовувати тільки для діагностики. Sprite Atlas для mutable destructible textures не використовувати.

Mask PNG імпортувати без втратної компресії та без mip maps. Якщо mask читається CPU, її колірний простір має бути linear, а фільтрація — Point.

## Відновлення позицій із master

Рекомендований pivot для runtime-фрагментів — центр `(0.5, 0.5)`, local scale — `(1, 1, 1)`.

Для віртуального production-полотна `productionCanvasWidth × productionCanvasHeight`, crop-прямокутника `x, y, width, height` із CSV і фінального `PPU`:

```text
centerX = x + width / 2
centerY = y + height / 2

unityX = (centerX - productionCanvasWidth / 2) / PPU
unityY = (productionCanvasHeight / 2 - centerY) / PPU
```

Повне production-полотно існує тільки як координатний простір і не імпортується в Unity. Усі фрагменти повинні використовувати однакові `production_scale` і PPU. Заборонено компенсувати помилки позиціонування випадковими scale-значеннями.

## Руйнування і колізії

Під час вибуху система повинна:

1. Знайти всі `DestructibleSurface`, world bounds яких перетинаються з кратером.
2. Перетворити центр і радіус кратера в локальні пікселі кожної поверхні.
3. Очистити відповідні пікселі visual texture.
4. Очистити ті самі пікселі mask.
5. Оновити змінену область спільної collision grid як об'єднання всіх активних масок.
6. Оновити GPU-текстури без створення нового `Texture2D` на кожен вибух.

Перекриття між поверхнями допустиме. Комірка спільної collision grid залишається твердою, якщо її займає хоча б одна активна руйнівна поверхня.

Тіні, світіння та інші нетверді пікселі visual texture не повинні створювати колізію. Джерелом твердості є mask, а не visual alpha.

## Пам'ять і продуктивність

- Не створювати runtime-копію повного master.
- Завантажувати тільки обрізані runtime-фрагменти поточної арени.
- Один мільйон RGBA32-пікселів займає приблизно 4 MB без урахування додаткових CPU-даних.
- Контролювати сумарну площу всіх активних runtime textures.
- Не зберігати зайві дублікати `Color32[]`, якщо вони не потрібні системі руйнування.
- Оновлювати collision grid і пікселі тільки в межах dirty region кратера.
- Не викликати повну перебудову всієї арени після кожного вибуху.
- Вивільняти runtime textures при завершенні бою.

## Перевірки інтеграції

Перед прийманням арени потрібно перевірити:

- Unity-композиція візуально збігається з master;
- немає щілин або ореолів на стиках;
- позиції не залежать від роздільності екрана;
- фон не реагує на вибухи;
- кратер на межі двох фрагментів змінює обидва;
- спільна collision grid не залишає невидимих твердих пікселів;
- тіні та світіння не створюють колізію;
- персонаж коректно стоїть на землі, конструкціях і ящиках;
- максимальний zoom не виявляє неприйнятного upscale;
- Android-збірка використовує ASTC 4x4 без автоматичного downscale;
- пам'ять і час застосування вибуху відповідають бюджету цільових пристроїв.

## Поетапне впровадження

1. Погодити модель `DestructibleWorld + DestructibleSurface`.
2. Реалізувати дві поверхні й тест вибуху через їхню межу.
3. Додати окремі mask PNG як джерело collision grid.
4. Автоматизувати складання prefab із CSV або Unity-конфігурації.
5. Інтегрувати одну повну арену.
6. Провести Editor, PlayMode та Android-перевірки.
7. Повернути production-компресію ASTC 4x4.
8. Позначити виконані кроки у відповідному design/architecture документі.
